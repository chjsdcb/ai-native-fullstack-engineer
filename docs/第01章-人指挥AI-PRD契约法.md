# 第01章 人指挥 AI：PRD 契约法

凌晨一点，学员老张把第三版方案发进群里："AI 已经帮我生成了完整的客服系统，你们看看。"

他学了三个月 AI 工具，从提示词技巧到各种插件，聊天框里无所不能。可当我们打开他部署的页面，登录接口直接 500，工单列表是写死的假数据，数据库里一张表都没有。他有点委屈："我明明跟 AI 说清楚了呀。"

问题不在 AI，在于他给 AI 的是一段"对话"，而不是一份"契约"。

## 对话没有约束力

你说"帮我做一个客服系统"，AI 会顺着你的话给出一个听起来很完整的方案——因为它被训练成迎合，而不是判断。它不知道你说的"客服系统"是给 3 人小团队内部用的，还是给十万用户公开访问的；不知道数据该存哪里，也不知道"做完"的标准是什么。

这不是 AI 的错，是你没有把需求变成契约。

契约和对话的区别只有一条：**契约有验收标准，而且验收标准可以被机器验证。**

## PRD 契约五要素

1. **背景**：为什么做这件事，解决谁的什么问题；
2. **用户**：谁在用，权限边界是什么；
3. **功能**：做什么、不做什么——边界和内容一样重要；
4. **选型**：技术栈与关键依赖，以及为什么选它；
5. **验收**：每一项功能"什么算做完"，用可执行、可量化的语言写。

对照一组反例与正例：

| 坏验收 | 好验收 |
| --- | --- |
| 界面要好看 | 首页在 Chrome 最新版加载耗时 < 2s，无控制台报错 |
| 登录要做出来 | `POST /api/auth/login` 成功返回 `code=0`；密码错误返回 401 与统一错误结构 |
| 数据要安全 | 所有业务表启用行级安全（RLS），未登录用户访问返回 403 |

一句话判断标准：**如果你验收时还需要人肉眼判断，这条验收就没写完。**

## 一份真实的 PRD 片段

```markdown
## 功能：工单创建
- 用户：登录后的客户
- 输入：标题（1–50 字）、描述（必填，≤2000 字）、优先级（低/中/高）
- 输出：POST /api/tickets 返回 {code:0, data:{id, status:"open"}}
- 校验：标题或描述为空返回 422；未登录返回 401
- 验收：创建成功后，工单出现在 GET /api/tickets 列表第一条，status 为 open
```

这段文字没有一句是"感觉"。AI 拿到它，生成的代码是可测的；你拿到它，验收是可执行的。PRD 契约法的全部功夫，就是让每个需求都长成这个样子。

在后面的内容里，你会看到这份契约如何一路传递：它约束 AI 生成的代码，约束数据库表的设计，甚至约束你向面试官讲述这个项目的方式。但现在，请先记住全书最重要的一句话：

**AI 负责写代码，你负责定义"什么是对的"。**

人指挥 AI 的全部秘密，都在这一句里。
